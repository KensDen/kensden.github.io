Compliance as Code

The Evidence Your Auditors
Expect — Automatically Generated

OSCAL (Open Security Controls Assessment Language) is the NIST-standard machine-readable format required for federal compliance submissions. Karrier generates it automatically on every pipeline run.

What is OSCAL and why does it matter?

OSCAL is the compliance format that NIST, FedRAMP, and DoD expect. Most organizations generate it manually — if at all — at the end of a project, requiring weeks of specialist time. Karrier generates valid OSCAL 1.1.2 documents automatically on every pipeline run, giving auditors machine-readable evidence that maps directly to specific controls.

Four frameworks. One pipeline run.

Most organizations pick one compliance framework and map to it manually. Karrier simultaneously maps every scanner finding to all four frameworks in a single automated pass — so a Trivy container scan automatically contributes evidence to NIST 800-53 SI-2, FedRAMP SI-2, NIST 800-171 3.14.1, and CMMC CM.L2-3.4.1, all at once.

Compliance as Code

Compliance Defined in YAML.
Evidence Delivered Automatically.

Karrier's control mappings are plain YAML files — readable by engineers and auditors alike. Thresholds, artifact linkages, and framework mappings are all version-controlled and fully auditable.

nist-800-53-rev5.yaml (excerpt) Control Mapping 
# NIST SP 800-53 Rev 5 — Karrier Control Mappings
# Override thresholds in project's .karrier-oscal.yml

framework:
  name: "NIST SP 800-53 Revision 5"
  version: "5.1.1"
  baseline: "MODERATE"

controls:
  SI-2:
    name: "Flaw Remediation"
    family: "System and Information Integrity"
    automated: true
    artifacts:
      - file_pattern: "dependency-check-report.json"
        parser_type: "trivy_vuln"
        scanner_name: "Trivy (Vulnerabilities)"
    thresholds:
      critical: 0      # Zero-tolerance
      high:     0      # Zero-tolerance
      medium:   10     # Up to 10 allowed

  IA-5:
    name: "Authenticator Management"
    family: "Identification and Authentication"
    automated: true
    artifacts:
      - file_pattern: "gitleaks-report.json"
        parser_type: "gitleaks"
        scanner_name: "Gitleaks"
    thresholds:
      critical: 0      # No secrets allowed — ever

  SR-3:
    name: "Supply Chain Controls and Processes"
    automated: true
    artifacts:
      - file_pattern: "dependency-check-report.json"
        parser_type: "trivy_filesystem"
        scanner_name: "Trivy (Vulnerabilities)"
      - file_pattern: "*-cyclonedx-sbom.json"
        parser_type: "cyclonedx_sbom"
        scanner_name: "SBOM Generation"
    thresholds:
      critical: 0
      high:     0

Every line has a reason.

Karrier's control mappings are not black-box configuration. Each entry is explicit, auditable, and version-controlled. Auditors, program managers, and engineers can all read the same file and understand exactly what is being assessed, how, and at what thresholds.

  • 1
    Control ID — maps directly to the framework control identifier (SI-2, IA-5). Cross-references are maintained automatically across all four frameworks.
  • 2
    artifacts — specifies which scanner output file provides evidence, which parser interprets it, and what human-readable name appears in the dashboard and OSCAL output.
  • 3
    thresholds — defines the pass/fail criteria per severity level. Critical and high are typically zero-tolerance. Thresholds can be overridden per-project without modifying the central mapping.
  • 4
    Multiple artifacts per control — SR-3 uses both Trivy and SBOM output. A single scan contributing to multiple controls, and a single control drawing from multiple scans, are both first-class patterns.
  • 5
    Version-controlled — every change to a threshold or mapping is a git commit. Auditors can inspect the complete history of compliance policy changes and see exactly what criteria applied at any point in time.
